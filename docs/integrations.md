# Integrations

A workspace connects an account at another service once (a Hetzner Cloud project, a DigitalOcean team, a Cloudflare account) and the rest of the panel uses it. This page is for contributors adding a provider. Hetzner Cloud is the reference: `app/Support/Integrations/Hetzner/`. DigitalOcean (`DigitalOcean/`) and Vultr (`Vultr/`) are built the same way.

## How it fits together

| Piece                                           | Where                         | What it does                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `integrations` table, `App\Models\Integration`  | one row per connected account | `provider` (catalogue key), `label`, `credentials` (cast `encrypted:array`, `#[Hidden]`), `fingerprint` (keyed hash, so one account isn't connected twice), `meta` (what the provider said, never secrets), `status` (`connected` or `failing`), `last_checked_at`, `last_error`, `created_by`. A workspace can hold several accounts of one provider unless `multipleAccounts()` says no. |
| `App\Support\Integrations\Provider`             | the contract                  | Connect form fields, `verify()`, capabilities, a summary line.                                                                                                                                                                                                                                                                                                                             |
| `App\Support\Integrations\ProviderClient`       | the HTTP base                 | Timeouts (15 s, 5 s to connect), three tries on 429 and 5xx, every failure turned into `IntegrationFailed` with a message a person can act on.                                                                                                                                                                                                                                             |
| `App\Support\Integrations\IntegrationProviders` | the registry                  | Built-in providers are registered in its constructor. A package can call `app(IntegrationProviders::class)->register(new MyProvider)` from its service provider.                                                                                                                                                                                                                           |
| `IntegrationCatalogue`                          | the Integrations page list    | Every row on the page. A provider's `key()` must match its catalogue key; the row then shows Connect, opens the connect dialog, and Manage goes to the account page.                                                                                                                                                                                                                       |
| `WorkspaceIntegrations`                         | page props                    | Adds each registered provider's accounts to the page and to the Connected rail.                                                                                                                                                                                                                                                                                                            |
| `IntegrationAccountController`                  | routes                        | `workspace.integrations.connect` (POST `integrations/connect/{provider}`), `.show` (the account page), `.check`, `.update` (rename), `.destroy` (disconnect).                                                                                                                                                                                                                              |

Cloud providers (anything with servers) also implement `App\Support\Integrations\Servers\ManagesServers`, and get the rest for free:

| Piece                                                                                               | What it does                                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `integration_servers`, `IntegrationServer`                                                          | The account's servers as last seen (`details` is `Server::toArray()`), and the machine each one is (`machine_id`, unique).                                                                                                                  |
| `CloudServers::sync()`                                                                              | Lists the servers, keeps them, drops vanished ones, and links servers to machines by public IPv4 or an address in their IPv6 network. Runs on connect, on Check again and when the account page loads its servers.                          |
| `CloudServers::claim()`                                                                             | Called from `DaemonEnrolController` when a daemon joins: a server made from ServerOS becomes that machine (by its join token), and an imported one is linked by address.                                                                    |
| `integration_operations`, `IntegrationOperation`, `ServerOperations`, `AdvanceIntegrationOperation` | Changes that take several calls (make a server, resize one). Each step waits on the provider's action, then the job dispatches itself again with a delay. Nothing blocks a page; the dialogs poll `workspace.integrations.operations.show`. |
| `CloudServerController`                                                                             | `server-options` (locations, types with prices, images, SSH keys) and making a server.                                                                                                                                                      |
| `MachineServerController`                                                                           | Restart, power cycle, resize types and resize, snapshots (list, take, delete) and deleting the server, under `machines/{machine}/server/...`.                                                                                               |
| `CloudInit::userData()`                                                                             | The cloud-init a new server starts with: Docker, then the panel's join command with a fresh enrolment token.                                                                                                                                |

The machine page shows the linked server from `CloudServers::machineProps()` (`cloudServer` prop on `MachineShow` and `MachineSettings`), and the dialogs live in `resources/js/components/machines/server/`.

## DNS and cache (Cloudflare)

`app/Support/Integrations/Cloudflare/` connects a Cloudflare account with a scoped API token (Zone Read, DNS Edit, Cache Purge) and keeps app domains pointed at their machines:

- `CloudflareDns::zoneFor()` matches a hostname to the longest active zone across the workspace's accounts (`*.example.com` matches `example.com`). Zones are cached for ten minutes as arrays.
- Every deploy fires `DeployQueued`; `PointDomainsAtCloudflare` queues `PointCloudflareDomains`, which adds or updates an A/AAAA record (a proxied CNAME to the tunnel when the machine has a Cloudflare Tunnel). New records are DNS only unless someone turns the proxy on per domain, so the machine's own certificate keeps working.
- `integration_dns_records` (`IntegrationDnsRecord`) tracks each record and whether ServerOS made it (`created_record`). When a deploy finishes, records follow the domains of the last deploy that worked (plus any still on its way); when an app's last container is removed, its records go. Only records ServerOS made are deleted at Cloudflare; ones it found or took over are left there. Disconnecting leaves every record in place.
- `CloudflareDomainController`: point a domain now (`domain-dns`, used by the domain check's "Point it here"), proxied on or off, purge the app's hostnames, and the per-app "purge after each deploy" setting (`app_settings[service].purge_cloudflare`).
- The domain check (`DomainCheckController`, MCP `check_domain`) adds `cloudflare` when the zone is on a connected account.

## Code hosts (GitLab)

`app/Support/Integrations/GitLab/` connects gitlab.com or a self-managed GitLab with a personal, group or project access token (read_api and read_repository; api to add webhooks). Providers that hold code implement `HostsRepositories`, which gives the account page its Projects tray, its "Used for" lines and what disconnecting stops.

- The instance address is https only. `GitLabClient` resolves it through `HostResolver` for every request and pins the connection to that answer (no redirects), so a private, loopback or link-local address is refused, as monitors and AI endpoints do.
- `GitLabRepositories::find()` maps a repository address to the account whose instance it's on (the first that can see it when several share one). It feeds the deploy dialog (`workspace.gitlab.repositories`, `workspace.gitlab.branches`), detection (`GitLabDetector`, called from `RepositoryDetector`), commit messages (`CommitMessages`) and the clone token: `DaemonJobQueue` adds the account's token as `repo_token` when the job is sent, only for an address on that instance, and it's never stored.
- Deploying each push: turning it on for a GitLab app (`AppVersionController::settings`) adds one webhook per project with its own secret (`gitlab_project_hooks`, `GitLabHooks::ensure()`). `POST /api/gitlab/webhook/{uuid}` checks `X-Gitlab-Token` against it and hands the push to `DeployOnPush`. `GitLabHooks::sync()` takes webhooks off when no app needs them (turned off, the app's last container removed, or the account disconnected).
- Merge request previews aren't built yet: `Previews` and the project settings only know GitHub repositories.

## Incidents and releases (PagerDuty, Linear, Sentry)

Providers that ServerOS sends things to implement `Incidents\DeliversEvents`; ones that open something when a problem starts and close it when it ends also implement `Incidents\RoutesIncidents` (`wants()`, the routing choices kept in `integrations.settings`, and their rules).

- `IncidentRouter` gets a `Problem` (a monitor down, a machine that stopped reporting, a critical or exploited CVE) from `MonitorAlerts`, `MachineWatcher` and `VulnerabilityAlerts`. Each problem has a stable key (`monitor:12`, `machine:4`, `cve:CVE-…`). `integration_incidents` keeps one row per account and problem; `open_key` is unique while it's open, so the same problem is never opened twice. `integrations:incidents` runs every minute: it opens what waits for a delay (Linear's "down for N minutes"), closes what recovered while nobody was looking, and sends failed events again.
- `integration_events` (`IntegrationEvent`) is what went out, shown on the account page with its state. `IntegrationEvents::deliver()` sends one at a time per incident, in order (a resolve waits for its trigger), tries passing failures (unavailable, rate limited) again after 1, 5, 15 and 60 minutes, and fails the rest at once; a refused key marks the account failing. A failed event can be sent again from the account page.
- PagerDuty: Events API v2 with `dedup_key` `serveros:{workspace}:{key}`; an update re-sends the trigger so the alert's details change. Disconnecting resolves the alerts ServerOS left open.
- Linear: the issue's id is made by ServerOS and sent with `issueCreate`, so a try after a lost reply finds the issue instead of opening another. Fixed issues move to the team's first completed state.
- Sentry: `integration_apps` ties an app (machine and service) to a project. `SentryReleases::jobFinished()` (from the gateway's `afterJob`) makes a release named after the commit, with the commit and repository, a deploy for the environment, and finalizes it; steps done are kept in the event's result so a retry doesn't repeat them. A roll back marks the older release deployed. `DaemonJobQueue::deploy()` sets `SENTRY_RELEASE` on a linked app. The service page's deferred `sentry` prop links each release and counts its new issues, cached for five minutes.

## OVHcloud

`app/Support/Integrations/OVHcloud/` connects one Public Cloud project through the OVHcloud API v1, with an application key, application secret and consumer key made on the region's token page (`OVHcloudProvider::RIGHTS`: GET `/me`, `/cloud/project`, `/cloud/project/*`, `/dedicated/server`, `/dedicated/server/*`; POST and DELETE `/cloud/project/*`). The endpoint (`ovh-eu`, `ovh-ca`, `ovh-us`) is picked in the form.

- `OVHcloudClient` signs every call in a request middleware, from the request as it's sent: `X-Ovh-Signature` is `$1$` and the SHA1 of the secret, consumer key, method, full URL, body and timestamp joined with `+`. The timestamp is on OVHcloud's clock: the difference from `/auth/time` is kept for an hour per endpoint and read again after a `QUERY_TIME_OUT`. `anonymous()` reads the public catalogue without keys.
- With one project the project field can stay empty; with several, verify lists them and asks for the ID. Flavors and images have an id per region, so types and images are named by their name and the id is looked up in the region when an instance is made or resized.
- Prices come from the public catalogue (`/order/catalog/public/cloud`, micro-cents, kept a day per subsidiary) by each flavor's hourly plan code. Instances are billed by the hour, so a month is 730 hours. Without the catalogue, types are offered without prices.
- Resize follows OVHcloud's rules: a classic model moves to one with a disk at least as big, a flex model to another flex model, never to Windows, GPU or Metal models. It happens in place and is followed by watching the instance. Restart is a soft reboot, power cycle a hard one. Snapshots are per instance (`/snapshot?instanceId=`).
- OVHcloud takes one SSH key when an instance is made: the rest go in through cloud-init (`CloudInit::withKeys()`).
- Dedicated servers are another API. They're listed (`dedicated:` ids) and linked by address, read only: the provider implements `Servers\LimitsServers`, so `CloudServers::capabilities()` gives them only `servers`, the machine page shows no actions and the server routes return 404. Keys without the dedicated rights simply list none. VPS (`/vps`) isn't covered.

## AWS (EC2)

`app/Support/Integrations/Aws/` connects an AWS account with an IAM user's access key ID and secret, and a default region. There's no AWS SDK: `AwsSigner` does Signature Version 4 (canonical request, string to sign, signing key from the secret, date, region and service), checked against AWS's published SigV4 test suite in `AwsSignatureTest`, and `AwsClient` signs every request in a request middleware, so a retry is signed again with a fresh date. It speaks the EC2 and STS Query APIs (form-encoded POSTs, XML answers turned into arrays by `AwsClient::xml()`, lists numbered `Filter.1.Value.2` by `flatten()`) and the JSON 1.1 APIs of Systems Manager and the Price List Query API. Only reads (`Describe*`, STS, SSM, pricing) and `RunInstances` (it carries a `ClientToken`) are tried again after a 5xx; throttling (`RequestLimitExceeded`, `Throttling`) is tried again for anything. AWS error codes become words (`AwsClient::failure()`): an unknown key or a secret that doesn't match lands on its own connect field, and a missing permission names the IAM action from AWS's message.

- **Connect.** The access key field shows the IAM policy to give the user (`AwsProvider::policy()`, exactly `AwsProvider::ACTIONS` plus `ssm:GetParameter` on Canonical's public parameters). Verify calls STS `GetCallerIdentity` (meta: account ID and ARN) and EC2 `DescribeRegions` in the default region, which proves EC2 access and that the region is turned on.
- **Regions.** An access key reaches every region, so servers are listed region by region. The provider implements `Servers\ChoosesRegions`: the account page's Regions tray (`CloudRegions::props()`, `PUT integrations/{integration}/regions`) picks the regions ServerOS looks in, kept in `integrations.settings.regions`; the default region is always one, and a region with a linked machine can't be dropped. Ids carry their region (`eu-west-2_i-0abc…`, `eu-west-2_snap-0abc…`).
- **Linking.** `DescribeInstances` in each region (everything but terminated), `DescribeVolumes` for the root volume's size, `DescribeAddresses` for Elastic IPs (`Server::$fixedIp`), and `DescribeInstanceTypes` for vCPUs and memory (kept a day). Instances link to machines by public IPv4, or IPv6 as a `/128`.
- **New instances.** Types are `AwsProvider::FAMILIES` up to 64 vCPUs, from `DescribeInstanceTypes` per region (kept a day). The image is the current Ubuntu 24.04 LTS AMI from Canonical's public SSM parameter for the type's architecture (amd64, or arm64 for Graviton). The instance goes in the region's default VPC, in a default subnet whose zone offers the type (`DescribeInstanceTypeOfferings`), with a public IPv4, IMDSv2, a 20 GB gp3 root volume, `Name` and `ManagedBy=ServerOS` tags, and the `serveros` security group, made once per VPC with 22, 80 and 443 open to everyone (rules changed there later are left alone). User data is the usual cloud-init, base64. An instance starts with one key pair, so the first picked key in its region is the `KeyName` and the rest go in through `CloudInit::withKeys()`. A region without a default VPC is refused with how to make one.
- **Prices** come from the Price List Query API (`GetProducts` on `api.pricing.us-east-1.amazonaws.com`, filtered to the region, Linux, shared tenancy, no preinstalled software, used capacity, `RunInstances` and `ANY_OF` the offered types), on-demand per hour × 730, kept a day per region. Without `pricing:GetProducts` the types simply show no prices.
- **Resize** stops the instance (a graceful stop, forced after a minute), sets `InstanceType` with `ModifyInstanceAttribute` and starts it again. Only types of the same architecture offered in the instance's zone are listed; the EBS disk stays as it is (`ServerRules::DISK_KEPT`). **Restart** is `RebootInstances`. **Power cycle** is a forced `StopInstances` and a `StartInstances` once it's off, as a `ServerOperations::POWER_CYCLE` change (`ServerRules::$powerCycleSteps`). Both dialogs warn that a stop gives the instance a new public IPv4 unless it has an Elastic IP (`ServerRules::$stopChangesIp`); the machine stays linked, since the link is kept by id.
- **Snapshots** are EBS snapshots of the root volume (`CreateSnapshot`, listed with `DescribeSnapshots` by volume, owner self), not AMIs: they need no reboot (`CreateImage` reboots by default), are incremental, and are one thing to delete rather than an image plus its snapshots. Restoring is done in the EC2 console (make a volume or an image from it). **Delete** is `TerminateInstances`; volumes set to stay and Elastic IPs stay in the account.

## Private networks (Tailscale)

`app/Support/Integrations/Tailscale/` connects a tailnet through the Tailscale API v2 with an API access token, or an OAuth client (secret in the token field, its ID in the client field; scopes `devices:core` and `auth_keys`). The tailnet is `-` for the token's own one. `TailscaleClient` swaps an OAuth client for an hour-long access token at `/oauth/token` and keeps it encrypted in the cache until just before it runs out. Endpoints used: `GET /tailnet/{tailnet}/devices?fields=all`, `POST /tailnet/{tailnet}/keys`, `DELETE /tailnet/{tailnet}/keys/{id}`, `DELETE /device/{id}`.

- `TailscaleDevices::sync()` keeps the devices in `tailscale_devices` and links each to a machine, only when it's the only match: the device ServerOS put there (`linked_by` `joined`), then a machine with the device's 100.x address on one of its interfaces, then one whose public IP is one of the device's endpoints, then one with its hostname. It runs on the account page (deferred `tailscale` prop) and while a machine joins. Machine pages read the rows (`tailnet` prop), so they never call the API.
- The daemon only runs commands inside containers (`service_exec`), so "Add to tailnet" deploys Tailscale's own image (`TailscaleInstall`, `services.tailscale.image`) as the `tailscale` app, on the host's network with kernel networking (`/dev/net/tun`, `NET_ADMIN`, `TS_USERSPACE=false`). The machine itself gets the tailnet address, and the state volume keeps it on the tailnet across restarts (`TS_AUTH_ONCE`). It needs Docker on the machine and the `deploy` job the daemon already has (`service.create` and `deploy.*` in its capability broker, refused in read-only mode).
- `TailnetChanges` makes a one-off, pre-authorized key with the account's tags (`integrations.settings.tags`, default `tag:serveros`) that runs out in `services.tailscale.key_minutes` (15). The key goes in as `TS_AUTHKEY` through `DaemonJobQueue::queue(secretEnv: ...)`, which adds it to the job's env as it's sent and never stores it; the daemon scrubs deploy env values from its own job record and log. `tailscale_changes` keeps the key's id, never the key, and `AdvanceTailnetChange` follows the deploy, waits for a device with that hostname, links it and revokes the key. A failure revokes it too.
- When the daemon can't (commands off, offline, no plan, read-only, no Docker, or Tailscale already installed by hand), the machine's Tailscale tray says why and `POST machines/{machine}/tailnet/commands` makes a key and hands back the commands to run (Tailscale's install script and `tailscale up --auth-key`), once, with `Cache-Control: no-store`. The device is still looked for and linked until the key runs out.
- "Remove from tailnet" runs `tailscale logout` in the container, removes it with its data (`service_remove`), then deletes the device. On a machine the daemon can't reach, the device is deleted now and the commands to clean up come back.
- The account page lists every device and which are machines, adds several machines at once (`POST integrations/{integration}/tailnet/machines`) and sets the tags (`PUT integrations/{integration}/tailnet`). Disconnecting leaves every device on the tailnet.
- Projects' private networks still use their own WireGuard network on public addresses; they don't use Tailscale addresses yet.

## Proxmox VE

`app/Support/Integrations/Proxmox/` connects one node or a whole cluster through the Proxmox VE API (`/api2/json`, [API viewer](https://pve.proxmox.com/pve-docs/api-viewer/)) with an API token, sent as `Authorization: PVEAPIToken=user@realm!tokenid=secret`. The address is https, port 8006 unless given. Endpoints used: `GET /version`, `/nodes`, `/cluster/status`, `/access/permissions`, `/cluster/resources?type=vm`, `/cluster/nextid`, `/nodes/{node}/tasks/{upid}/status`; under `/nodes/{node}/qemu/{vmid}`: `GET`/`PUT config`, `GET pending`, `PUT resize`, `GET status/current`, `POST status/{start,stop,shutdown,reboot}`, `POST clone`, `GET`/`POST snapshot`, `DELETE snapshot/{name}`, `DELETE ?purge=1&destroy-unreferenced-disks=1`, `POST agent/ping`, `GET agent/network-get-interfaces`, `POST agent/exec`, `GET agent/exec-status`; `GET /nodes/{node}/lxc/{vmid}/interfaces`.

- **Address safety.** Like GitLab, `ProxmoxClient` resolves the host through `HostResolver` for every request and pins the connection to the answer, with no redirects. A private or loopback address is refused, except on a self-hosted panel with `MONITORS_ALLOW_PRIVATE=true` (the error says so there); link-local never works.
- **Certificates.** Proxmox makes its own certificate, so the form takes its SHA-256 fingerprint (the `AB:CD:…` form from System › Certificates is fine). With one, the request goes through Guzzle's stream handler to the pinned IP with the `Host` header, `verify` off and `stream_context.ssl.peer_fingerprint`: PHP checks the certificate in the handshake, before a byte of the request (or the token) is sent, so verification is replaced by the pin rather than turned off. Without one, curl verifies the certificate as usual. A mismatch or an untrusted certificate comes back as words about the certificate, on the fingerprint field (`IntegrationFailed::$field`).
- **Verify** reads the version, nodes, cluster name and the token's effective privileges. A token without `VM.Audit` is refused; other missing privileges ServerOS uses are shown on the account page (`VM.Monitor` before Proxmox VE 9, `VM.GuestAgent.Unrestricted` from 9 for the install). The address, token and fingerprint are kept in their tidy form (`ConnectedAccount::$credentials`).
- **Servers.** A server's id is its VMID; the node is looked up for each call, since VMs move. Actions are task UPIDs, longer than other providers' ids, so `integration_operations.action_id` holds 255 characters. Addresses come from the guest agent, then a container's interfaces, then the fixed `ipconfig0` address, kept for five minutes. IPv6 is kept as a `/128` so neighbours on one `/64` don't link to each other. LXC containers are listed and linked read only: the provider implements `LimitsServers`, so they get only `servers`.
- **New VMs** use the shared pieces for providers without types: `ServerRules::SIZING_CUSTOM` and `SizesFreely` (cores, memory and disk by hand), `ServerImage::$location`, `$size`, `$agent` and `$cloudInit` (a template, where it lives and what it has), and `PreparesServers` (a full clone in `create()`, then `prepare()` sets cores, memory, `ciuser`, URL-encoded `sshkeys` and `ipconfig0`, grows the disk and starts it). The operation shows "Make the server" while the clone runs.
- **The install.** Proxmox's API can't upload cloud-init snippets, so the user data can't carry the install. The provider implements `RunsCommands`: once the VM runs, `ServerOperations` pings the guest agent and runs `CloudInit::script()` with `agent/exec` (`bash -s`, the script as input, so the token isn't in the process list), then waits for the daemon to join as usual. A template without the agent, or an agent that doesn't answer within ten minutes, turns the step into the one-line command (`CloudInit::oneLine()`), shown in the dialog and on the account page while the change is open. Both are kept encrypted in the operation's input. A failed run fails the change with the end of its output, tokens taken out.
- **Resize** sets `cores` and `memory` and grows the boot disk (`PUT resize`, grow only, within the host's cores and memory). Proxmox applies memory live with memory hotplug and NUMA on, and cores only on a restart; anything still in `pending` is applied with `status/reboot`, or left for the next restart when the person unticks "Restart it now".
- **Power cycle** is a hard stop and a start through `ServerRules::$powerCycleSteps`. **Snapshots** are the VM's own, without RAM; ids are `vmid-name`, names are made from what was typed and the text goes in the description. Rolling back is left to Proxmox. **Delete** stops a running VM and destroys it with `purge`, which also takes it out of backup jobs, replication and HA.

## Images (Docker Hub)

`app/Support/Integrations/DockerHub/` connects one Docker Hub account per workspace (`multipleAccounts()` is false) with a username and a personal access token; Read-only access is enough. Organizations go in an optional field, since the [Hub API](https://docs.docker.com/reference/api/hub/latest/) has no route that lists a token's organizations. `DockerHubClient` swaps the token for a ten-minute access token at `POST /v2/auth/token` (kept encrypted in the cache for nine) and only uses the namespace-scoped routes: `GET /v2/namespaces/{namespace}/repositories`, `.../repositories/{repository}/tags` and `.../tags/{tag}`. Verify counts the repositories of the account and each organization (meta: username, organizations, repository count).

- **Registry login.** `Provider::connected()` runs after connecting and after each Check again that works. Docker Hub's keeps the workspace's `docker.io` login (`container_registries.integration_id`) in step with the account, so `DaemonJobQueue` sends it with deploys as before. A login for the same Docker ID is taken over, not duplicated; one for another Docker ID is left until someone presses "Use this account for pulls" on the account page (`POST integrations/{integration}/docker-hub/registry`). Saving a docker.io login by hand in Settings unlinks it. Disconnecting removes the login the account keeps.
- **Deploying an image.** The deploy dialog lists the repositories (`workspace.docker-hub.repositories`, kept five minutes) and a repository's tags with push dates, sizes, platforms and the port an `EXPOSE` layer names (`workspace.docker-hub.tags`). `POST machines/{machine}/deploy/image` asks the registry which digest the tag points at (`RegistryClient::digest(fresh: true)`, the same client the image update checks use) and queues an ordinary app deploy from `ImageDeploy::job()`: no repository, one file, `Dockerfile` = `FROM docker.io/ns/name:tag@sha256:…`. The daemon builds a release from it like any app (health check, swap without downtime, releases kept for rolling back), named after the digest (`ImageDeploy::commitOf()`). `ImageDeploy::isApp()` is what the panel now asks instead of "has a repository" to treat a deploy as an app. `docker_hub_apps` keeps which repository and tag each app came from.
- **Redeploy on push.** The Hub API reference documents no webhook routes (the webhooks page mentions creating them through the API, but the reference has no such endpoint), so ServerOS doesn't add them. Turning it on for an app (`PUT machines/{machine}/apps/{service}/docker-hub`) makes the app's webhook address, `/api/docker-hub/webhook/{secret}` (40 characters, only its sha256 is looked up, the address is kept encrypted to show again with a copy button). The app's image card says "Waiting for the first delivery" until Docker Hub calls it. Docker Hub signs nothing, so the secret is the proof; the payload's `repository.repo_name` must be the app's repository (422 otherwise) and `push_data.tag` its tag (others are ignored). Deliveries are limited to `DockerHubApps::PUSHES_PER_MINUTE` per app. `RedeployImageApp` asks the registry for the tag's digest again and, when it's new, redeploys the app's last deploy with it through `DeployOnPush::queuePush()` (waits behind a running deploy, a newer push replaces a waiting one), as whoever turned it on. Activity: `app.image_push_setting`, `app.image_pushed`, `app.push_skipped`.
- **Updates.** `ImageUpdates::check()` compares the digest an image app's live release was deployed from with the tag's digest at the registry, so these apps show on Updates like any container with a newer image, and updating one there redeploys it with the new digest (`DockerHubApps::update()`) instead of an `image_update`. The app's page shows the same in its Image card, with Update now (`POST machines/{machine}/apps/{service}/docker-hub/update`).

## Adding a provider

1. **Catalogue.** Make sure `IntegrationCatalogue::all()` has the row and its `logo` exists in `BrandLogo`. Its key is your provider's `key()`.
2. **Client.** Extend `ProviderClient` with `baseUrl()`, `providerName()` and `headers()`. Override `providerMessage()` to pull the API's own error text, and `failure()` for codes worth their own words (a read-only token, a project limit). Use only documented endpoints. Paginate with a loop like `HetznerClient::all()`.
3. **Provider.** Extend `Provider`:
    - `key()`, `name()`.
    - `fields()`: a `ConnectField` per input. `secret: true` fields render as password inputs and are never sent back. Give `help` (where to click to make the token, and the least access it needs), `link` (the page where it's made) and `rules`. A field without `required` in its rules is optional in the form. A field with `options` is a choice, and an option's own `link` replaces the field's while it's picked (OVHcloud's token page per region).
    - `verify(array $credentials)`: one cheap read that proves the credentials reach an account. Return `new ConnectedAccount($suggestedLabel, $meta)`. `meta` is shown and kept in plain JSON, so only names and counts. Throw `IntegrationFailed` (the client already does) and its message becomes the form error, under the first secret field unless its `field` names another. When verify settles a field the person left empty (which project), return it as the third argument, `credentials`: it's kept with the others, so Check again finds the same thing, and the account can't be connected twice that way.
    - `capabilities()`: `Capability` cases. Add a case (with its label and description) when you need a new one.
    - `summary()` for the Connected rail, `facts()` for the account page.
4. **Servers (cloud providers).** Implement `ManagesServers`. Map the provider's objects to `Server`, `ServerType` (prices per location, the locations it can be made in now), `ServerImage` (mark one `recommended`; Ubuntu LTS where there is one), `SshKey`, `Snapshot`. Methods that start something return the provider's action id, or `null` when the provider has no action to follow (Vultr): `ServerOperations` then watches the server itself, waiting for it to run after a start and to show the new type after a resize. `action()` turns an id into `ActionState`. `rules()` returns `ServerRules`: whether a resize needs the server off (Hetzner, DigitalOcean) or happens in place (Vultr), whether growing the disk is optional (Hetzner's `upgrade_disk`, DigitalOcean's `disk`) or always happens, whether it can go smaller, whether a restart is gentle, and whether snapshots belong to the server or the whole account. The dialogs word themselves from it. Filter `resizeTypes()` to what the provider accepts (same architecture and storage, a disk at least as big, or the provider's own list of upgrades). Override `describe()` when a capability works differently there.
5. **Register** it in `IntegrationProviders::__construct()` (or from a package).
6. **Copy.** Every string a person reads goes through `__()` / `$t()`. Plain and short, no em dashes.
7. **Tests.** A fake of the API in `tests/Support/` like `FakeHetzner` (it keeps servers, actions and snapshots, records calls, can fail the next call to a path), installed with `Http::fake()` and `Http::preventStrayRequests()`, so no test reaches the real API. Cover at least: connect success and refused credentials, credentials absent from props and Activity, permissions, linking by address, each action's request body, and a failure that leaves things as they were. `Sleep::fake()` keeps the retry waits instant.

## Rules

- **Credentials stay on the server.** Never put `$integration->credentials` in props, JSON, logs, Activity meta or exception messages.
- **Permission.** Everything uses `manageMachines` unless a capability needs more. Check `$integration->workspace_id === $workspace->id` in every action: `{integration}` is not scoped to the workspace by the router.
- **Audit.** Every write route is `#[Audited]` and records an `Activity` (or calls `AuditContext::nothingChanged()`). Add an `ActivityLine` entry for each action; `integration.*` is in the "Workspace and billing" group, server actions are `machine.server_*` and `machine.snapshot_*`.
- **Never block a page.** Short calls (a restart, a snapshot) run in the request with the client's timeouts. Anything that waits on the provider runs as an `IntegrationOperation`.
- **Leave things as they were on failure.** A resize that stopped the server starts it again before giving up; a server that couldn't be made gives its join token back.
- **Cache arrays, not objects.** `cache.serializable_classes` is off, so a cached object comes back as `__PHP_Incomplete_Class`. Cache `toArray()` and rebuild (see `ServerPlans::fromArray()`).
- **POSTs aren't retried after a server error,** only when the provider turned them away unread (429), so nothing is made twice.
- **If the catalogue key already has a state** from elsewhere in the panel (Cloudflare tunnels, PagerDuty workflow steps), merge it in `WorkspaceIntegrations::accounts()` instead of replacing it.
